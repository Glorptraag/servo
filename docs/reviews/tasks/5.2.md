## Questions for Drew

1. **D96 with a short Run in between.** A fault shows in Run A, Run B stops before that tick without showing it, then Run C runs past the tick without it. The model keeps the fault open through B and counts C as the fix, if C's build differs from A's on the part (model.ts:110). The strictest reading of D31 + D96 would take B as "the next Run in which it no longer appears", find that it did not pass the tick, and close the fault as not fixed. The tick used is the one in the latest showing Run, not the very first. **Default: keep as built.** A Run the child stopped early has not tested the fix, so waiting for one that does is the fairer record.
2. **parent.html reaching into packages/parent's source (finding 2).** Accept the documented relative entry for launch? The alternative is to move the web build's composition to packages/tools, which may depend on everything, or to give packages/parent its own Vite page that the release step merges into `dist/release/web`. **Default: accept for launch, and add the guard test from finding 2.** Revisit when 6.3's release pipeline is next touched.
3. **Estimating time in the sandbox from Run times** (the sum of `endedAt − startedAt` over sandbox Runs). **Default: no, keep it absent per D39.** Run time measures only Run mode, not the building that makes up most sandbox time, so it would understate it and read as a real figure.
4. **Should parent.html also ask for the tester invite code (6.3)?** Today `startPage`'s invite gate guards only index.html, so in a tester build `/parent.html` opens to the parental gate without a code. It shows only what is already on that device; an uninvited visitor has no Runs, but could add child profiles. **Default: leave as built for now, and fold it into the open 6.3 release question about tester builds.** If tester builds must be fully closed, the parent page should call the same `openThroughInviteGate` before mounting.
5. **Fault times counted from `startedAt`.** `firstSeen` is the first showing Run's `startedAt`, and `fixedAt` is the fixing Run's `startedAt`. So "Fixed in n Runs and t" includes the first Run's own play time and excludes the fixing Run's. Alternatives: from the first Run's `endedAt` (when the child had seen the fault), or from `startedAt` plus `firstTick`, to the fixing Run's `startedAt`. **Default: keep `startedAt` to `startedAt`, as 0.4's interface states** ("where time-to-fix starts"). At minute resolution the difference is small, and the line says "counted from the Run that first showed it".
