## Review points

1. **SIM-4 reading: contact switches count.** Right. `warmControls` varies every control of kind `switch`, and the graph does not tell a manual switch from a contact switch. A bumper switch is moved by its probe and is a position the Run reaches, so skipping it from the count would let a build with six manual switches and one bumper warm 2^7 = 128 positions, or leave the bumper's positions unwarmed. The review's own count for busy-workbench (SIM-2: "4 switches and 4 channels") includes the bumper. The task text says "manual switches" loosely; the builder's reading matches the code and the review. The `WARM_SWITCHES` name and the comment say "switches, manual and contact", which is clear.
2. **Warm-up change is behaviour-neutral.** `warmControls` only fills caches keyed by what decides their value; it reads no clock or randomness (rule 2). Goldens are all same and the 100x determinism sweep is the proof of byte equality. Builds with more than 6 switches are left cold exactly as before, and builds of 5 or 6 controls with at most 6 switches are warmed as before.
3. **New test.** It builds eight controls (asserts 8, of which 4 are switches), warms, asserts 16 cached wirings, flips each of the three manual switches in turn and then all back, asserting the cache size is 16 after every tick and the set of keys is unchanged. It fails against the old rule (see Checks), so it guards SIM-1. It covers `model.wired` only (finding 2).
4. **One settingValue.** `settingValue(setting, placed)` now lives in electrical/primitives.ts and is imported by behaviour/params.ts; the electrical model reaches it through a private `boundValue` that finds the setting for a primitive and param. ## Findings

1. **Low, `packages/sim-core/src/loop/warm.ts:6`, `:15` (and `docs/loop.md:79`).** The cost bound is wrong now. The comment says "2^6 = 64 settings, each searching at most 63 others". That held when only switches were controls. With channels, each position's search tries the alternatives of every control (`alternatives` in `packages/schema/src/circuit/wired.ts:394`, single-control changes only above `CONTROL_COMBINATION_CAP` = 1024, `wired.ts:60`), so a position can try up to about 1,000 combinations or, above the cap, one change per control option. loop.md:79 says "channels included" two sentences after "at most 2^6 = 64 positions", which is true but does not give the bound that matters (setup time). No measurement of `createSimulation` on busy-workbench was recorded; I tried a one-off timing and the console output did not come through, so the figure is not measured here. busy-workbench has 2^4 x 3^4 = 1,296 combinations, above the cap, so it uses the single-change path. Proposed fix: state the bound as positions x alternatives (cap 1,024), and time `createSimulation` on busy-workbench under load, noting the figure in loop.md beside the 6–120 ms already recorded (line 118).
2. **Low (follow-up), `packages/sim-core/src/electrical/needs.ts:186-227`.** The situations cache still grows inside a tick on the first flip of a switch (the `explain` alternatives search for voltage-way needs), so a flip can still search in a tick even for a warmed build. The new test asserts the wiring cache only, as the task asks; the loop.md bullet on "voltage-way needs" and electrical.md "Not done here" both say so. Queue it as its own task (warm the situations for each switch position, or measure and accept). Proof: the builder's report; the same code path is described in docs/electrical.md:138-143.
3. **Low, `packages/sim-core/src/behaviour/params.ts:2`.** Behaviour now imports from `../electrical/primitives.ts`. Before, the two modules did not reach into each other in src (the electrical tests import `speedRule` from behaviour, which is tests only). The dependency is one function and lint is green, but README and loop.md do not mention that behaviour depends on electrical, and a shared setting helper would sit more naturally in a neutral module. Proposed fix: either accept and add one line to docs/behaviour.md, or move `settingValue` to `src/graph/` and import it from both.
4. **Low, `packages/sim-core/test/busy-workbench.json`.** A 747-line frozen copy of a content fixture, adapted in test code, with no check that it still looks like the content one. The README exception is written down. If the content fixture changes, the copy and the claim "eight controls, three manual switches" quietly diverge. Proposed fix: replace it with a small schema-fixture build that has three manual switches, a bumper switch and two driver channels (about 80 lines), or move the test to packages/tools against `@servo/content/fixtures`, where real content is the convention. If it stays, add a test line that the copy equals the content fixture's hash or that its control counts hold.
5. **Info, `packages/sim-core/src/electrical/primitives.ts:30`.** SIM-4 also said the two bindings disagree on non-finite values: params.ts drops them (`Number.isFinite`), `speedSettings` clamps without the check (`Math.min(1, Math.max(0, NaN))` is NaN). Sharing `settingValue` removes the duplicated mapping but not this difference. A blueprint cannot hold a non-finite setting (schema validation), so it is not reachable today. Proposed fix: add the finite check in `speedSettings` for symmetry in a later tidy, or note the difference in electrical.md.
6. **Info.** `mapSettingValue` is imported by both files in the old code; now only primitives.ts imports it. The `PlacedPart` and `Setting` type imports are used. No dead code left in the changed files.
