## Data safety: attempts to lose a build

| Attempt | Outcome |
| --- | --- |
| Offline edits racing a reconnect | Safe. `applyPull` reads the row and its waiting change inside one transaction (the save's tables plus `sync`), so a save made during the network pull is seen. `recordChange` deletes and re-adds the change, so a save made between `outbox` and `markPushed` gets a new `seq` and stays waiting |
| Two tabs | Safe. Sync runs under a Web Lock per database. When sync replaces the build open on the canvas, the canvas's next save keeps the synced version as a copy, by the store's two-tab rule (README decision 9). Nothing is lost, but one version may be kept twice |
| Dexie v1 → v2 with existing data | Safe (probe above) |
| Service worker update mid-edit | Safe. The worker has no `skipWaiting`, so the old worker and its cache serve the old page, lazy chunks included, until every old page is closed. The cache is deleted only on `activate`. A new tab opened meanwhile also gets the old build, so two schema versions never run side by side |
| Ties, clock skew, a removal racing an edit, a pushed change coming back | No loss found. The losing version is always pushed as a copy in the same push as the winner |

## Findings

1. **Minor · data safety (sync liveness) · `packages/app/src/sync/engine.ts:89`.** When the host cannot be reached while `navigator.onLine` is true (home router up but internet down, a school captive portal, the host down), sync goes to `offline` and never retries by itself. Recovery needs an `online` event, which will not come because the browser already thinks it is online, a `now()` call or the next app start. Nothing is lost, since the store is local-first, but "sync on reconnect" does not cover a host outage. The `failed` path already has a 2 s → 30 s backoff; the unreachable path could reuse it.
2. **Minor · conflict rule ("runs are only ever added") · `packages/app/src/sync/changes.ts:271`, `:285`.** A removal of a run or card game is applied unconditionally. The remover's profile removal sends a removal for every run it owned. A device that keeps the profile because a build was changed there offline (README decision 5) therefore keeps the profile and the build but loses that profile's runs and card games. The test at `test/sync/sync.test.ts:291` checks only blueprints. Suggested fix: apply run and card-game removals only when the profile itself goes.
3. **Minor · done-when strength · `packages/app/test/browser/offline.test.ts:109–110`.** The offline phase is a reload of the same tab, with the same renderer and the same running worker. It also never asserts `controlled: true` once offline. The cached-paths equality and the offline `fetch` of every file show the worker serves the build, so I accept the done-when. A cold-start variant would be stronger: close the page, open a new page in the same context while offline, and assert that the page is controlled.
4. **Note · D11 · `packages/app/src/offline/plugin.ts`.** Rapier offline cannot be tested until the Run loop lands. Task 4.4, or the next task that adds a lazy Rapier import, should extend the airplane-mode e2e to press Run offline.
5. **Minor · data safety (precision) · `packages/app/src/sync/changes.ts:77`, `:315`, `:352`; `packages/app/src/store/index.ts:191`.** `base` carries only the parent version's `meta.updatedAt`. The device stores `<updatedAt>#<hash>`, but only the timestamp travels. A version is taken as "made from the version here", replacing it without a copy, when the timestamps match.
   - If two devices save one build in the same millisecond, a version from the other lineage can replace the local one.
   - I traced the tie cases and found the replaced version is always on the remote and kept as a copy by the device that pushed the winner, so this is not a loss today.
   - Sending the hash as well would make the rule exact rather than safe by the copy that travels beside it. This is worth settling before D13 freezes the wire format.
6. **Minor · duplicate copies · `packages/app/src/sync/engine.ts:66–67`.** If a page closes after `remote.push` resolves but before `markPushed` commits, the device's synced version is not updated. When that push comes back and the build has changed here since, the device keeps a copy of its own older version. This produces a duplicate, not a loss. A device id on changes, or an idempotent push, would avoid it (for D13).
7. **Minor · liveness · `packages/app/src/sync/remotes.ts:63`.** `httpRemote` has no request timeout. While a request hangs, the Web Lock is held, `state` stays `syncing`, and other tabs' syncs wait. This is dormant until a host is configured.
8. **Nit · docs · `packages/app/src/store/database.ts:68`.** The `SyncRow` JSDoc says the value is the `meta.updatedAt`. It is `<updatedAt>#<content hash>`, as store.md says.
9. **Minor · rule 13 · `packages/app/README.md` "Decisions and open questions".** The ten decisions are documented in the README, but none is in the decision queue: `pharao.py decision list` has nothing for 5.5. The orchestrator should queue at least decisions 2, 4, 5, 7, 8 and 10 (the questions below).

## Questions for Drew (each with the default the build proceeds on)

1. **Updating to a new build.** A new build waits until every tab of the old one is closed, and on an iPad a Safari tab can stay open for weeks. Should the app show a quiet line ("A new version is ready; it opens next time"), or reload by itself at a safe moment, such as on the library screen?
   Default: keep waiting silently, as built.
2. **Saying that a copy was kept.** When sync keeps the other device's version as a copy, should Save's line say so ("A copy of the other version was kept")?
   Default: say nothing until a host exists. The copy appears in the library with `keptFrom`.
3. **When sync runs.** Sync runs on open, on reconnect and when asked, not on a timer and not after each save.
   Default: as built, plus a retry for an unreachable host (finding 1) once a host exists.
4. **A profile removed on one device while a child built in it offline on another.** The second device keeps the profile and the build. Should it also keep that profile's runs and card games (finding 2)?
   Default: keep them, since runs are only ever added.
5. **Wire format (D13).** Should `base` carry the content hash, and should pushes carry a device id or be rejected when their `base` is not the host's current version (findings 5 and 6, README decision 7)?
   Default: add the hash and the device id when D13 names a host. No change before then.
6. **Install to the home screen (web app manifest).** This was left out, but it affects Safari's storage eviction (docs/stack.md).
   Default: no manifest. The store's `persist()` request stands.
