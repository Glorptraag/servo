## Questions asked

1. **The two gaps are real rule-8 breaks on touch, of different weight.**
   - **Wire gap (genuine).** `hitTest` (packages/canvas/src/scene/hit.ts) returns ports first, then the topmost wire within WIRE_HIT_MM/2. A wire wholly under sockets and a wire drawn over it has no point that reaches it. Touch and pointer therefore cannot select, bin or drag that wire, while the list view removes it. The child can only uncover it by moving a part.
   - **Wheel gap (weaker, but real).** Placement.md decision 7 says a tap on the part being moved leaves it where it is. For a carried wheel the free spot overlaps its own tile, so tap-then-tap cannot land the wheel there, and a tap elsewhere lands at the nearest free spot. The action exists on touch; one landing spot does not.
   - **Are they hidden?** Both are named in the e2e README "Findings" (items 1 and 2) and in code comments (plan.ts:127, plan.ts:357, paths.ts `pressableLine`). Neither has a test that fails today.
   - **Would a fix be covered without edits?** No. The `move` tour takes a mount-held part and `pressableLine` skips unpressable lines, so a fix would not widen the suite. Someone would have to edit `plan.ts` and `paths.ts`.
   - **Is a regression hidden?** For the wire gap, partly. `pressableLine` takes the first pressable wire, so a regression that made more wires unpressable would pass until none is pressable. For the wheel gap, a wheel that stops moving by tap would still be missed, because the tour never moves a carried wheel.
   - **Is there a canvas task for either?** I found none (grep of status.json titles). See Question 1 below.
2. **Settings and Reset arena through `apply`: an acceptable stand-in, not a hole.**
   - Neither control is a canvas gesture; each sends one command. The parity check proves the command gives the same bytes on every path.
   - On main, `packages/app/test/browser/controls-run-bar.test.tsx` covers Reset arena, Undo, Run, Slower and Faster by touch, pointer and keyboard on the real App. `controls-panels.test.tsx` does the same for a Level 2 card's setting, with ArrowRight on the radio, plus arena presets, props and Read aloud.
   - The two layers together cover the control and the command. The README states the stand-in (item 11 and the "A setting goes through `apply`" paragraph).
3. **Strict fails on a mismatch**, as the plant above shows. The default is `parityStrict = SERVO_PARITY_STRICT !== '0'` (vitest.config.ts).
4. **The CI change is an added shard only.** It adds `parity-4` with `strict: '1'` and updates two comments. The 10-minute timeout is unchanged, and `e2e-ci-shards.test.ts` passes.
5. **The testing.ts change is tools-only and additive in effect.** Prop handles (move, bin) now come from `propHandlePlaces`, and the bin from `wiring.binPlace` only. The `handles()` doc comment is updated. The old bin-for-a-prop mapping is kept through that map, and canvas tests pass.
6. **Shard timing.**
   - My parity-3 shard took 419 s of test time. The builder's four shards took 7:51, 7:53, 8:42 and 8:12, a spread of 51 s, so they are balanced to about 10%.
   - I think the headroom is thin. The 10-minute `timeout-minutes` also covers checkout, install, Playwright and `pnpm art`, perhaps 1 to 2 minutes. A 2-vCPU runner is slower than this machine, and CI has no 7.6 run behind it yet.
   - The default of one tour per fixture was chosen for this reason, but I would expect the longest shard to sit at 9 to 10 minutes of the budget.
