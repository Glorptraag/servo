# Review R-6.6 · Task 6.6 Level 3 slot behind a flag (branch task/6.6 at 284097a)

Verdict: PASS

The flag is off by default and stored per device. With it off, nothing from Level 3 shows: no program view, no angle on the card or in the list view, and no program is passed to a Run. With it on, only the servo motor's angle unlocks. It is picked out by its data (a number setting bound to a position actuator's `target`), and the card's slider and the list view both offer it. In a Run, a powered microcontroller then sweeps the servo motor to that angle and holds it there. sim-core, schema and content are untouched. Every check I was asked to run is green.

The merge into current main has one conflict, in `packages/app/src/App.tsx`. It is mechanical (see Merge). I found no blocking issues, only minor points and questions.

I ran on Node v26.3.0 and pnpm 12.8.1, at load averages around 11–15. `git status` in the worktree was clean before and after. I changed nothing in any checkout.

## What I checked

- **Off by default and per device.** The key is `servo.flags` in localStorage (`FLAGS_KEY`, flags/index.ts:76). `App` uses `givenFlags ?? deviceFlags()` and reads them once (App.tsx:37).
- **Nothing leaks with the flag off:**
  - `unlocked` is passed to `SpecCard` only when `slot` is on (App.tsx:64), `ProgramView` renders only when `slot` is on (App.tsx:65), and so does `unlockSettings` on `mountCanvas` (App.tsx:76).
  - With no `unlocked`, `cardModel` filters settings exactly as before (spec-card/model.ts:91). With no `unlockSettings`, the list view does too (canvas list-view/actions.ts:136).
  - The browser test confirms it in the app: with the flag off there is no angle on the card or in the list view and no program view, and a Run shows the servo motor's no-signal line at 90°.
  - With the flag on, the DC motor's speed and the LED's colour stay locked on the card and in the list view. A unit test pins `slotSetting` to `servo-motor.angle` out of the content's three Level 3 settings.
- **The Run loop:**
  - App passes `program` to the Run bar only when `slot` is on (App.tsx:69), and `programFor` returns `undefined` itself when the flag is off (program-view/runtime.ts).
  - The Run bar always hands the loop a `program` callback (run-bar.tsx:77). With the flag off that callback returns `undefined`, and run-loop.ts:200–201 then leaves `program` out of `createSimulation`, so every brain is the no-op brain (D41).
  - `git diff main...task/6.6 -- packages/sim-core packages/schema packages/content` is empty (rule 2).
  - The runtime keeps no state and is pure. It is written against `ProgramRuntime` from `@servo/sim-core`'s public interface, as packages/sim-core/docs/program.md ("Exports") allows.
  - A unit test checks determinism: the same build gives the same events tick for tick.
- **Canvas `unlockSettings`:**

  - It is documented in the interface doc comment and in packages/canvas/README.md (the mount-option paragraph and the list-view section).
  - It reaches only the list view's settings filter, through `ListHost` and `ListState`. The new canvas code imports only `@servo/schema` types, and lint's package-map rule stays green, so the canvas still reaches sim-core only through its interface.

## Findings

1. **Minor · rule 5 / rule 2 (replay) · packages/app/src/sharing/replay.ts:44, run-bar/run-bar.tsx:68–80.**
   - The shared-build replay builds its `RunLoop` without `program`, so a build shared from a device with the flag on replays with the no-op brain. Its servo motor holds and hums instead of sweeping.
   - The run recorder stores the blueprint but nothing that says a program drove the Run. A Run recorded with the flag on therefore cannot be reproduced from its record alone.
   - Nothing reaches this today, because the content has no microcontroller (D102). It matches the open point in packages/sim-core/docs/program.md ("Where a brain's rules live"), and the app README's decision 4 notes it. It needs settling before a brain part ships (Question 2).
2. **Minor · rule 10 / product · App.tsx:64, 76; packages/app/README.md "Feature flags".** With the flag on and the real content, the servo motor's angle slider and list action appear at Level 1, but no placeable part can carry a signal to it. Setting the angle therefore changes nothing in a Run: the servo motor still holds at 90° and hums. The README documents this and D102 accepts it for testing, but a tester who turns the flag on in the real app sees a control that does nothing (Question 1).
3. **Trivial · reuse · packages/app/src/flags/index.ts:37.** The private `pageStorage` copies the shell's exported `pageStorage` (packages/app/src/shell/edges.ts:38, exported at shell/index.ts:5) line for line. The flags module could import it.
4. **Trivial · reuse · packages/app/src/program-view/program-view.tsx:14.** `midSentence` copies the canvas's `midSentence` (packages/canvas/src/list-view/words.ts:17). The canvas does not export it, so a copy is defensible, but the two can drift.
5. **Trivial · test strength · packages/app/test/browser/program-view.test.tsx:197–238.** The byte-identical test rebuilds App's composition by hand: a `Shell` at level 1, a `SpecCard` with `unlocked`, and `mountCanvas` with `unlockSettings`. It does not use `App`, so a later change to App.tsx's wiring would not fail it. The real-App test drives both paths too, but only checks the shown angle, not bytes.
6. **Note · scope · process rule 11.** The task names `src/program-view/` and `src/flags/`. The branch also changes App.tsx, the Run bar and loop (a new optional `program` option), the spec card (a new optional `unlocked` prop and `cardModel` parameter, plus a new `UnlockedSetting` type export) and the canvas (`unlockSettings`, which the orchestrator ruled on). Each change is additive, defaults to the old behaviour, and is noted in the package READMEs (app README "Feature flags" and spec-card README; canvas README). No action is needed.
