## Findings

1. **Major · task description ("goal detection from run records") and the 4.4/5.2 contract · packages/app/src/run-bar/record.ts:8, :66, :102.**
   - **The gap.** The recorder still keeps every Run as a sandbox Run. It sets no `challenge` and no `goal`, it reads earlier Runs with `challenge: null`, and it numbers `runNumber` per build. The schema says a challenge Run is numbered among the child's Runs of that challenge (schema/src/types/run.ts:145).
   - **What depends on it.** 5.2's "unscripted builds passed" (and "parts met", if read from part introductions) has nothing to reconcile against. 4.6's "after two Runs that miss the goal" also needs a per-Run verdict.
   - **Why it matters now.** 5.1 is done, so `pharao.py done 4.5` releases 5.2 at once.
   - **The fix.** Pass the current challenge's id and the `GoalWatch` verdict into `RunRecorder.end`. The verdict is in hand, because `judgeRun(challenge, record, catalogue)` can run on the record before it is stored. Then number and link Runs per challenge when there is one.
2. **Minor · D48 / rule 9 · packages/app/src/challenges/goal.ts:105, :161.**
   - **The problem.** The named fault is resolved by `placed` id, for example `{ placed: 'motor-right' }`. New parts always get fresh `p<n>` ids (schema/src/validate/blueprint.ts:116). So a child can delete the backwards motor, place a new DC motor, wire it backwards again and flip its Direction setting. Its `reversed` fault is then on an unnamed part, and the breakdown passes. That is exactly what D48 is meant to stop.
   - **Suggested fix.** When a named `placed` target is missing from the build that ran, fall back to the same failure on any part of that type, or to `'any'`.
   - The same weakness will reach 4.6's ladders, which use the same targets.
3. **Minor · rule 8 · packages/app/src/challenges/arena-strip.tsx:103.**
   - **The problem.** The keyboard and screen-reader path is chosen by `event.detail === 0`. A screen-reader activation that arrives with `detail` 1 would start a tap-then-tap placement, and that user cannot finish it on the canvas. iOS VoiceOver's double-tap on the target iPad may do this.
   - **Suggested fix.** Verify on a device, or also offer the canvas list view's "place" for a pending prop.
4. **Minor · rule 8 · packages/app/src/challenges/arena-strip.tsx:128.**
   - **The problem.** In a challenge, the presets the challenge does not use are `disabled`, so keyboard and screen-reader users never reach their spoken reason ("This challenge sets the arena.").
   - **Suggested fix.** Use `aria-disabled`, as 4.4 did for Run (R-4.4 finding 3).
5. **Minor · product · packages/app/src/App.tsx:52, :73–74.**
   - **The problem.** Which challenge is on the canvas lives only in React state. Two cases lose it:
     - a reload, where the app reopens the newest build, possibly a challenge build;
     - reopening a challenge build from "Saved builds".
   - **The effect.** In both cases the build shows as a sandbox build at `START_LEVEL`, with no goal line and no kit. For a Level 2 build, that also re-locks the Direction setting.
   - **Status.** This is acknowledged in README Q3. It wants the same blueprint-to-challenge link as finding 1 (Q3).
6. **Minor · tests · packages/app/test/challenges/goal.test.ts:147–167.**
   - **The gap.** The breakdown cases call `judgeRun` alone, not `verdictOf`, so the agreement between the live and record verdicts is not asserted where the sticky-fault logic lives.
   - **A related gap.** `pnpm golden` exercises the judge on no fixture until 4.7 adds one with `expect.goal`.
7. **Nit · packages/app/src/challenges/home.tsx:163.** New build pressed while saved builds are still being read names the build from an empty list, which can give a duplicate "Build 1".
8. **Nit · packages/tools/src/golden-runs/main.ts:12.** Content fixtures are now read when the module loads, not lazily inside `cases()`.
9. **Info · scope.**
   - The changes outside `packages/app/src/challenges/` were assigned by the orchestrator: App.tsx, the `./goal` export, the app README, and the golden-runs main.ts and README.
   - No other package's code was changed.
