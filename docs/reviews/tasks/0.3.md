# Review R-0.3 · Task 0.3 Blueprint versioning and migrations (branch task/0.3 at 04d5d22: builder commits e9fa314 and 04d5d22, on top of the task/0.2 merge 458dcc4)

Verdict: PASS

The done-when is met and both checks pass. `migrateBlueprint` never threw on 40,000 hostile or mutated inputs, and a newer version is refused on both the migrate and validate paths. The hand-written SHA-256 matches `node:crypto`, and V8 and JavaScriptCore give the same derived ids. All five findings are minor: one is about scope and decision process, and four are about messages, docs and future versions.

The review questions, probe by probe:

- **Never throws.** I ran 40,000 rounds of 1 to 3 random mutations of both fixtures.
  - Half the rounds used JSON values only. The other half used hostile values:
    - revoked and throwing Proxies, and throwing and alternating getters;
    - cycles, objects nested 10,000 deep, arrays nested 100,000 deep, and a sparse array of 5 million slots;
    - BigInt, Symbol, functions and `toJSON`;
    - null-prototype objects, Map, Set, Date and typed arrays.
  - Nothing threw. Every refusal had codes from `ISSUE_CODES`, a `$` path and a message.
  - Every accepted result passed `validateBlueprintShape` and had a UUID v4 id.
  - No refusal of JSON data had the "After migrating…" prefix. So the step's reader is at least as strict as the v1 structure check, which is what migrations.md:24 claims.
- **Future versions.** These are refused, never guessed:
  - Versions 2, 2^53+2 and 1e308 give `blueprint.newer_version` at `$.version` from both `migrateBlueprint` and `validateBlueprint`, with the same message.
  - A version 2 document that is otherwise garbage gets that one issue only.
  - A version that is missing, text, null, -1, 0.5 or not finite is refused with a `value.*` code.
- **SHA-256.** It is hand-written, not a platform API. Web Crypto's digest is asynchronous, and the schema takes no library. It uses only typed arrays and DataView: no clock and no randomness.
  - It matched `node:crypto` on 3,369 inputs:
    - every length from 0 to 1,100 bytes, three random messages each;
    - lengths around 4 KiB and 64 KiB, and 100 KB;
    - 0x00, 0xff, 0x80 and 0x7f fills around block edges.
  - `utf8` matched `TextEncoder` on 20,000 random strings, including lone surrogates and astral characters.
  - `derivedUuid` matched a reference construction on 5,000 texts.
- **The derived id.**
  - Both pinned ids (`9470c6db-…` and `47334c53-…`) recompute with `node:crypto` from `servo-blueprint-v0\n` plus `canonicalJson(stored)`.
  - The version and variant bits are correct, and every id I generated matches `UUID_V4`.
  - It is the same across engines. I bundled the code with rolldown and ran it in V8 (Node) and in JavaScriptCore, Safari's engine, through `osascript -l JavaScript`.
    - The inputs were the 2 fixtures and 400 seeded random v0 documents. They hold fractional and extreme floats, -0, 5e-324 and 1.79e308, accented and astral characters, and lone surrogates.
    - Both engines gave the same ids and the same serialised bytes for all 402.
  - Time zone and locale make no difference: the default (Brisbane) and `TZ=Pacific/Kiritimati` with a `tr_TR` locale give the same ids.
- **Tests for each step.**
  - `v0ToV1` has its own suite. It covers:
    - every rename, all four quarter turns, and timestamps from 1970 to 9999;
    - the pinned ids, independence from key order, and a change of id for each change of content;
    - the high-water marks, including `p007`, ids with no number, and the next ids claimed;
    - purity: a frozen input, and no object shared with it;
    - 29 strict refusals, each with a named reason;
    - never throwing.
  - The runner is tested with made-up steps: order, finding a step by its version, the refusal prefix, a throw turned into `value.unreadable`, a gap in the steps, and a newer version.
  - A list test keeps `BLUEPRINT_MIGRATIONS` contiguous from 0 to `BLUEPRINT_VERSION`.
- **Cost.** Running it on every load is cheap:
  - a 10-part build took 27 ms on a cold first call, and 100 parts took 14 ms;
  - 1,000 parts with 2,000 wires (540 KB) take 123 ms;
  - 5,000 parts (2.7 MB) take 466 ms.

## Findings

Paths are relative to `packages/schema/`.

1. minor · rules 13 and 14 · src/validate/blueprint.ts:146-149, src/fixtures.ts:132, src/types/issue.ts:50 · The change reaches outside the task's files (`src/migrate/`, `fixtures/v0/`) and changes task 0.2's merged contract.
   - `validateBlueprint` now answers a version above 1 with the new code `blueprint.newer_version`. So do `validateChallenge` and `validateRunRecord`, which go through it.
   - The recorded reason of the `version-2` invalid fixture changed with it.
   - In its favour: it fits "refuse, never guess", is documented (migrations.md:23, validation.md:83), is tested and merges cleanly.
   - Against it: e9fa314 wrote both points down as open questions, and 04d5d22 settled them in the branch instead of queueing them with `pharao.py decision add`.
   - It needs sign-off as a change to 0.2's interface (question 1).
2. minor · — · src/validate/blueprint.ts:150-159 · `validateBlueprint` still ends its message with "Migrate it first" for versions that `migrateBlueprint` can never migrate. I probed -1, 0.5, "1", "2" and 1e400 (Infinity).
   - `ISSUE_CODES` and validation.md:82 still describe `blueprint.unsupported_version` as "not version 1", though newer versions now have their own code.
   - Fix: say "Migrate it first" only for whole numbers below `BLUEPRINT_VERSION`.
3. minor · rule 5 · src/migrate/v0-to-v1.ts:4-5, docs/migrations.md:40 · The step is meant to be frozen, but it depends on code that version 1 owns.
   - It imports `idNumber` from the v1 validator and `canonicalJson` from the v1 canonical module.
   - Its reader is built from kit primitives that v1 shares: `readName`, `readLevel`, `readSlug` and `UUID_V4`.
   - A later change to any of these would silently change what v0 → v1 accepts or writes, including the high-water marks and derived ids. Only the two pinned fixtures would catch it.
   - So migrations.md:40 ("later changes to the current readers never change it") claims too much. The version 2 recipe should also say to freeze copies of these.
4. minor · rule 5 · docs/migrations.md:81-86 · The version 2 recipe covers stored blueprints only.
   - Run records (src/validate/run.ts:171) and challenge starts read the blueprint inside them with the current reader.
   - So after a version bump, stored run records stop validating unless their snapshots are migrated too (question 3).
5. minor · — · docs/validation.md:31, docs/documents.md:15 · Both docs still say every blueprint id is a random UUID v4 that the app generates, and that a duplicate gets a new id.
   - A migrated v0 blueprint's id is derived instead: a SHA-256 hash laid out as a v4 UUID. RFC 9562 would call a SHA-256 name-based id version 8.
   - So identical stored v0 documents share one id.
   - Only migrations.md:60-66 says so. This does not matter while v0 is synthetic, but both docs should point to the exception.

## Questions for Drew

1. Should every validator refuse a blueprint from a newer version of Servo (version above 1) with `blueprint.newer_version` and a "from a newer version of Servo" message? Today, on main, they answer `blueprint.unsupported_version` with "Migrate it first". This changes task 0.2's contract. Default if unanswered: keep the change, since an older app meets newer blueprints after sync and cannot migrate them.
2. Should a migrated blueprint keep a derived id?
   - Today `meta.id` is a SHA-256 of the stored document, so the same document gets the same id on every device and every load, even before it is saved. Identical stored documents share one id.
   - The alternative is a random id, written back on the first load.
   - Default: keep the derived id. v0 is synthetic, and the draft store in task 0.4 loads blueprints by `meta.id`, so it needs an id it can reproduce before the first save.
3. When the blueprint version is bumped, should stored run records have their blueprint snapshots migrated, or be kept as stored and read with a frozen older reader? They feed the progress view in tasks 5.x and the Section 14 measures. Default: migrate the snapshot with `migrateBlueprint` on load, keeping `blueprintId` unchanged.
