## Builder's notes, checked

- **"Twin parts are numbered by id."** True (`words.ts:42-54`, natural order, `p2` before `p10`). The renumbering this causes is question Q3.
- **"Move to a free spot picks the free spot nearest the middle of the build."** True. `freeMoveSpot` (`actions.ts:50-69`) anchors on the middle of the bounding box of everything outside the moved part and what it holds, then calls `movedPartSpot`. A root part already at that spot is not offered a move (`actions.ts:89`).
- **"Space never presses a list-view button (D42)."** True. `dom.ts:305-307` cancels the default action of Space's keyup on any button, which stops the click in Chromium. WebKit applies a button's Space click in its default handler, which the same cancel should stop. The browser test checks this in Build mode and Run mode. This is stricter than D42, which only says Enter flips a switch. See Q2.
- **"Only Rolling Start, Reversed Motor and Short Circuit can be built from the list alone."** True, for the reason above: loose-part coordinates.
- **"Mounting relies on the app tray offering `placementsFor`."** Only partly true. **Mounting itself is reachable by keyboard and screen reader inside the canvas package's own DOM**:
  - a part's actions include "Move X to <mount point>" (`moveTargets`) and, for a hub, "Move X onto <shaft>";
  - a mount port's actions include "Mount X on …";
  - a mount point's actions include "Mount Y on <this>".

  My probe shows that placing a part at the free spot and then mounting it gives the same bytes as a touch drop straight onto the mount point. What depends on the tray is **placing a new part at all** (finding 1).
- **"Select buttons throw until 3.4 lands."** True. `ListViewModel.perform` calls `CanvasSurface.select`, which throws `notYet('select', '3.4')` (`surface.ts:335`). The DOM click handler (`dom.ts:285-302`) does not catch the error. See finding 4.

## Findings

1. **Major · rule 8 · `packages/canvas/README.md:47`, `src/list-view/dom.ts:130-192`.** The list view's DOM has no way to place a new part or a new prop.
   - That path exists only as `canvas.listView.placementsFor(type)` and `propPlacementsFor(prop)`, and the README says the app tray offers them.
   - This matches the 0.4 interface ("Where a tray part can go", `interface.ts:434-437`). The touch and pointer paths also start from the tray (`beginPlacement`). So leaving the tray path to the app is acceptable, and the canvas package delivers all three APIs together.
   - However, task 4.2's done-when ("Tray shows exactly the kit's parts; library overlay opens …") does not require a keyboard or screen-reader path that calls `placementsFor`, and 4.9 does not either. If nothing changes, a screen-reader user cannot place a single part. Gate G3 ("the list view drives the same build") would then fail, or get waved through.
   - Fix (plan, not code): before G3, add to 4.2's done-when that every tray tile and arena-strip prop has a keyboard and screen-reader path that lists `placementsFor` / `propPlacementsFor` and performs one, with the same bytes as a touch drop. 3.8's parity check should then place parts through the tray's path, not by calling `placementsFor` directly. See Q1.
2. **Minor · rule 8 · `src/placement/controller.ts:222-225`, `src/list-view/dom.ts:354-391`.** Task 3.2 left `placement.notice` "for the list view to read out (task 3.6)". 3.6 does not read it. Two effects:
   - The canvas's own lines are never announced to a screen reader: the removal line for a removal made on the canvas, and the "held" line when a held part is tapped.
   - The two paths describe the same removal differently. The canvas says "Removed with it: 2 wires. Loose now: large wheel"; the list's live region says "Removed DC motor 1. Large wheel 1 is loose now".

   Within the list view's own actions, its announcements are complete, so this is minor. See Q4.
3. **Minor · rule 8 · `src/renderer/surface.ts:165-174`, `src/list-view/model.ts:39-42`.** The surface builds the model without `live` or `hint`, and `changed()` is never called per frame.
   - In the real canvas, Run mode never fills `ListPart.live` or `ListProp.live`, and `hint` is always undefined. A switch's label comes only from what the list itself sent, or from the part record's starting state.
   - These hooks belong to 3.5 (`applyRunFrame`) and 3.4 (`showHint`), and both still throw. Those tasks must pass `live` and `hint` into `ListHost` and call `list.changed()` on each frame. Otherwise Run-mode readouts and hint text twins never reach the list.
   - The README says "its state from the frame's `closed` readout when frames have come". The canvas has no code that gives the list a frame yet.
4. **Minor · rule 9 · `src/list-view/dom.ts:285-302`, `src/renderer/surface.ts:335`.** Every "Select …" button throws an uncaught error until 3.4 merges. On a read-only canvas, Select buttons are the only buttons, and in Run mode they show on every part. If 3.6 reaches G3 before 3.4, Drew will meet buttons that do nothing and log errors.
   - In the same handler, when `perform` returns false (an action that has gone stale), nothing is said in the live region. The screen-reader user hears silence.
5. **Minor · rule 8 · `src/list-view/dom.ts:184`, `src/list-view/actions.ts:299-306`.** Props are not numbered the way parts are.
   - Two boxes give two "Actions for box" buttons and two "Select the box" or "Remove the box" actions. In a screen reader's list of buttons they cannot be told apart.
   - The prop's line does tell them apart (size and direction), but the button names do not.
6. **Minor · process (scope) · `src/renderer/surface.ts`, `test/browser/handle.test.ts`.** The task's files are `packages/canvas/src/list-view/`. 3.6 also edits `surface.ts` (+31/−4) and one handle test line.
   - Both edits are necessary: they connect the model to `apply`, `control` and `select`, replace the `listView` stub that named task 3.6, and refresh the list on rebuild, mode change and level change.
   - Both edits are small, and `interface.ts` is unchanged. They are noted, not objected to.
7. **Minor · performance · `src/list-view/model.ts:164-173`.** The snapshot cache only works in Build mode. In Run mode, every read of `parts`, `wires` or `props` rebuilds everything, and one `render()` reads them several times. This is harmless today, because Run mode does not re-render per frame (finding 3). It will cost frame time once 3.5 calls `changed()` on every frame.
