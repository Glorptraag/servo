## Probes

1. **Every content fixture (19) and every valid schema blueprint (7), with their inputs.** The schema blueprints ran 45 ticks with every manual switch flipped.
   - At every tick: the independent fold of the event stream equals `frame.live`. The events keep the documented order. Frames and events are frozen. `live` has one entry per part, then per prop.
   - Records cut every 15 ticks and at each input tick all pass `validateRunRecord` (174 cuts).
   - **Snapshots.** I took about 370 snapshots, at:
     - tick 0, every 9th tick and the middle;
     - each input tick, after `input()` and before the step that applies it, and the 3 ticks after;
     - 1 and 2 ticks before each fault event, while its debounce count is running.
   - **Restores.** Each snapshot was restored into the same Simulation, and 72 into a fresh twin.
     - Re-snapshotting gives the same bytes.
     - The restored frame equals the original.
     - Every later frame, and the final record, is identical to the unbroken Run.
   - A replay from the record's own blueprint, seed and inputs gives the same record.
   - A second process, running the 26 cases in reverse order, gave identical record and frame hashes.
2. **Debounce edges.** I tested `debounceFaults` directly, then the public API on `switch-across-pack`.
   - Exactly 3 active ticks: the fault shows at the 3rd and ends at the 3rd inactive tick.
   - 2 active ticks: never shows.
   - A gap of 2: the fault never ends. A gap of 3: it ends, then starts again 3 ticks later.
   - A flicker resets the count. Two failure modes count separately.
   - A short that lasts the last 2 ticks of a Run never shows.
   - A short whose 3rd tick is the last tick shows there. The record lists it at that tick, with its start event, and validates.
   - The short's current shows on every one of its ticks.
   - Restores at 2 of 3 ticks into a start, and at 2 of 3 into an end, replay exactly in a twin.

## Findings

1. minor · rule 2 / N14 warm-up · packages/sim-core/src/loop/warm.ts:11-17, docs/loop.md:79 · The warm-up skips any build with more than 6 controls, counting driver channels. But it only varies the switches.
   - `busy-workbench`, a Level 2 content fixture, has 8 controls: 4 switches and 4 channels. So it is not warmed. Tick 0 searches once inside `createSimulation`, and the first flip of each of its 3 manual switches searches inside a tick.
   - At load 265, those ticks took 20–146 ms, against 8 ms for a plain tick at that load.
   - The comments "none at Levels 1–2" and "a Level 1–2 kit has at most 4" are wrong for this fixture.
   - Counting only the switches (16 positions here) would warm it.
2. minor · interface (rule 14) · packages/sim-core/src/interface.ts:93-97 · `restore` says it "Throws when the snapshot came from another Simulation". A twin's snapshot (same fingerprint) is now accepted (loop.md decision 2, README updated). Note this as an interface change, or reword the comment at the next interface touch.
3. minor · replay · packages/sim-core/docs/runs.md:28 · An input made at the last tick is recorded at tick = `ticks`, and the record validates. This happens when a child flips a switch and presses Stop before the next step, which is likely in slow motion.
   - A replay that applies each input before stepping, up to `ticks`, drops it, so the replayed record's `inputs` differ. `stepTo` and the tools `play` both work that way.
   - Applying the trailing inputs after the last step gives an identical record.
   - Document the replay rule for task 1.7's harness and the app's replay.
4. minor · R-1.3 note for 1.5 · src/electrical/primitives.ts:16-74, src/behaviour/params.ts:10-53 · The speed rule and the setting binding still exist twice (`steadyRpm`/`speedSettings`/`settingValue`, and `settledPrimitives`/`settingValue`). ## Questions for Drew

1. **D31, how `fixed` is worked out.** sim-core cannot see the canvas's edit commands, so `fixed` lists the differences between the two Runs' blueprints that touch the faulted part, its ports or its wires. A wire removed and put back between Runs counts as no change. Accept that reading of D31?
   - Default if unanswered: accept it, as built.
2. **A fix made on another part.** A motor driver that browned out is fixed by a bigger battery pack. If the pack is swapped by deleting it and wiring a new one, `fixed` shows only the driver's re-made wire. If it is retyped in place, `fixed` shows no change at all. Should `fixed` also count changes to the part that fed or explained the fault?
   - Default if unanswered: no, D31 as written (only the faulted part, its ports and its wires).
3. **Debounced fault timing (D74).** A fault's `firstTick` and its start event come at its 3rd active tick, so the first is tick 2. Time-to-fix measures shift by 0.07 s. Keep it?
   - Default if unanswered: keep it, as built.
