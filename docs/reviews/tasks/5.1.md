### Trying to land an edit under the wrong child

**By reading:**
- Every blueprint write runs in one `rw` transaction over `profiles` that first calls `requireProfile` (blueprints.ts `write`; records.ts likewise). IndexedDB serialises it against `profiles.remove`, so a save can never commit after its child is removed.
- Every save goes through `job.child`, the scope the edit was made in. The Autosaver keys each job by profile and build.
- `show()` (index.ts:120) remounts the app under a new key with the new child's own opening, so the old child's build never reaches the new scope.

## Findings

1. **Major, non-blocking for this merge (rule 4 spirit, the done-when "switch isolates builds"): an open app page ignores the switch and removal.** `app/src/index.ts:71–78` resolves the profile in use once, at mount. Suppose the adult switches from Robin to Sam in the parent page while the app is open in another tab. Sam then sees Robin's builds in that tab, and every edit autosaves into Robin's records. If Robin was removed instead, the tab keeps showing Robin's build in memory. Its saves are refused, so it writes a fresh journal note holding Robin's build, and that note stays in localStorage until the app next opens (`recover` drops it then, autosave.ts:251). Store data never crosses between children, but what the child at the screen sees does. Default: the app listens for the `storage` event on `servo.profile:<db>` and on its own profile's removal, flushes pending saves to the old child, then reopens for the new one. Make it a follow-up task in packages/app that must merge before the parent page is reachable (finding 2).
2. **Minor (D28): no page of the web build mounts the parent view.** `parent/src/index.ts:114` exports `mountParent`, but no HTML entry, vite input or Home link calls it. D28 says the parent view is "reached from Home through a parental gate". The switch can't be reached in the product yet. Default: a follow-up task wires a parent page and a link from Home (4.5), outside app's import graph.
3. **Minor (robustness): "the only profile is in use" is implicit, not stored.** `app/src/store/profiles.ts:67–72`. On a single-profile device, a second profile created by any path other than `addChild`, such as direct `store.profiles.create` or a future sync pull, leaves no one in use. The child's app then silently drops to "Builds are not being kept on this device". Related: when the page cannot keep the choice, `parent/src/accounts/model.ts:61` swallows the `use()` failure, and adding a second child then leaves no one in use with no way to choose. The adult learns this only after the add, from the `noneInUse` line. Default: when localStorage cannot keep the choice, `addChild` refuses with a line, and store.md notes that a sync pull must pin the profile in use before adding profiles (for D10's sync task).
4. **Minor (isolation of system text): replay's kept-copy line reaches whichever child opens.** `app/src/shell/autosave.ts:261` emits `keptCopy` for a note of any profile. With 5.1, the app can open for Sam while the replayed note was Robin's, and Sam's Save line then says "A copy of the other version was kept". No name or build leaks. This is pre-existing from 4.9, and 5.1 makes it reachable. Default: emit it only when `note.profile` is the profile the app opens.
5. **Minor (rule 8, keyboard and screen reader).**
   - Focus falls to `<body>` after "Remove profile" (`view.tsx:179–182`) and after "Save name" (`view.tsx:174–178`), because the focused row or form unmounts.
   - The inline confirm group (`view.tsx:254–262`) gives focus to "Keep profile" but does not tie the warning paragraph to the group. A screen reader may announce the buttons without saying what is deleted.

   Touch, pointer and keyboard paths do all exist, through native radio, button and text controls, at 44 px or larger, and the tests exercise them. Default: after a removal, move focus to the switch's legend or the next child's radio. After a rename, return focus to that row's Rename button. Add `aria-describedby` from the group to the warning.
6. **Minor (test gap): the app's opening of the chosen profile is untested.** Nothing tests the `app/src/index.ts:71–78` change through `mountApp`, for example "two profiles, Sam chosen: the app opens Sam's newest build", or "two profiles, none chosen: unsaved line". The parent tests assert `store.profiles.inUse()` only. Default: add a case to the app browser store test once task 4.9's fix there lands.
7. **Nit: `NameRefused` says "A name is 1 to 60 characters."** (`parent/src/accounts/model.ts:34`). Control characters are also refused, and a rename made only of tabs would get a message that doesn't fit. Default: leave as is. Control characters are hard to type on a tablet.
