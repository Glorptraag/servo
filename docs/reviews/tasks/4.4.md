## Findings

1. **Medium: rule 4 spirit and D31 data integrity.** A Run stopped in its spin-up is kept as a 0-tick record (run-loop.ts:292, record.ts:55). sim-core's `fixedFaults` (packages/sim-core/src/recorder/changes.ts:73) marks every fault of the previous Run that this Run did not show as "fixed". Here is the sequence:
   1. The child runs, sees a fault and stops.
   2. They press Run and Stop at once, or double-tap Space.
   3. That second record claims the fault was fixed, with no changes, and becomes the `previous` of the next real Run, which then cannot link the fault.

   This is permanent store data that the parent progress view will read. A Run that stops before the fault's onset tick has the same effect in milder form, and that part is a D31/sim-core matter. Suggested fix: keep only Runs with `simulation.tick > 0` (one line in `halt` or `RunRecorder.end`). See Q1.
2. **Medium: robustness.** Every Run, including one with a reused Simulation, waits on IndexedDB before the spin-up. `RunRecorder.start` awaits the previous Run's `runs.add` and then `runs.list` (record.ts:45-47), and the loop awaits it as `onStart` (run-loop.ts:186, :204). A rejected store is handled. A store that stalls, as with WebKit IndexedDB hangs or a blocked `versionchange`, leaves Run in `loading` with no spin-up, so a store problem does stop a Run, against the README's own line. Suggested fix: take `startedAt` at the press and compute `runNumber` and `previous` in `end()`, off the Run's critical path. At the least, bound the wait.
3. **Low: rule 8.** With nothing placed, the Run toggle is `disabled` (run-bar.tsx:179), so it leaves the tab order. A keyboard or screen-reader user tabbing through the bar never lands on it to hear its `aria-describedby` reason. The `role="status"` line is announced only when it appears. `aria-disabled="true"` with the click guarded would keep it focusable.
4. **Low: brief table "Run enabled only when at least one part is placed".** During `loading` the canvas is in Build mode. If the child removes every part, the loop re-reads the build and runs it empty (run-loop.ts:211-214), and the bar shows Stop. This is harmless but outside the stated rule. The re-read could end the Run when `now.parts.length === 0`. Also during `loading`, Undo is off (`building` excludes busy) while other edits are allowed, which is a small inconsistency.
5. **Info: 5.6 behaviour.** In two places, replay.ts now behaves slightly differently:
   - `onChange` fires once per tick, not once per animation frame, and first reports `('running', 0)` before the first step. view.tsx uses only the phase, so nothing visible changes.
   - Stop during loading now discards the made Simulation instead of keeping it, so the next play rebuilds it with the same seed and gets the same run, at the cost of a reload.
6. **Low: duplication.** packages/tools/src/gate/run.ts:31 (`GateRun`) still has its own copy of the loop. The builder flagged this (README, item 7). It needs a follow-up task to point the gate tool at `RunLoop`, which means exporting it from `@servo/app`, with the export path agreed against the package map.
7. **Info: rule 7.** The text is clean: no exclamation marks, no praise, real units ("ticks a second"). The failure line "This Run could not be shown on this device." needs 3 lines in the 148 × 52 px slot at 14 px. It fits, but only just.

## Questions for Drew

- **Q1.** Should a Run stopped before its first step (in the one-second spin-up) be kept as a run record? It would count toward run numbers and could mark a fault "fixed" (D31). **Default:** no. Keep only Runs with at least one tick. Raise separately whether D31's "fixed" should also need the new Run to last past the tick at which the fault first appeared.
- **Q2.** Should Space never activate a focused button anywhere in the app, so that Space is always Run/Stop (D42), with Enter activating buttons? **Default:** yes, as built. Revisit if switch-access or other assistive setups that send Space are in scope for launch.
- **Q3.** Should the clock speed persist per child across visits? **Default:** no. It starts at 30 on each visit, as built.
- **Q4.** Should Run wait for the store to number the Run before the spin-up starts (finding 2)? **Default:** no. Number and link the Run when it ends, so the store is never on Run's path.
