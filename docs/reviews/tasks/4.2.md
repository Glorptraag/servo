# Review R-4.2 · Task 4.2 Part tray and Parts Library (branch task/4.2 at e8c668d)

Verdict: FAIL

All three done-when criteria hold, and so do D84 and `user-select: none`. Every command I was asked to run is green. One major finding fails the review.

The CI fix for the Back swipe set `touch-action: pan-y` (`pan-x` in portrait) on the tray and its tiles. As a result, a touch drag that starts along the tray's axis never reaches the canvas. The browser takes the gesture as a scroll and sends `pointercancel`, so the part is not placed and nothing tells the child. In landscape, that is any drag from a tile steeper than 45 degrees. That is the main way a 6–8-year-old places a part (brief Section 10), so the touch path of ground rule 8 is only partly delivered. The suite misses it because every test drag is horizontal.

The rest are minor findings and questions. The branch conflicts with main and with task/4.5 in two files each (see Merge).

I ran on Node v26.3.0 and pnpm 12.8.1. `git status` in the worktree and in the main checkout was clean before and after. I changed nothing in any checkout. My extra probe tests ran from a scratch directory outside the repo, with its own Vitest config, against the worktree's sources.

## Findings

1. **Major · ground rule 8, brief Section 10 (place a part: drag a tile onto the canvas)**
   - **Where.** packages/app/src/tray/tray.css:11, :19, :83, :90, with tray.tsx:930–931.
   - **What happens.** A touch drag from a tile that starts along the tray's axis is lost: more vertical than horizontal in landscape, more horizontal than vertical in portrait. `touch-action: pan-y` (or `pan-x`) hands the gesture to the browser, Chromium sends `pointercancel`, and the press is released. The part is not placed, and nothing on screen shows why.
   - **Who it hits.** A child aiming at the canvas from a tile near the top or bottom of the tray drags diagonally as often as not. I measured landscape down-right at dx 300 / dy 420 and up-right at dx 250 / dy −400. Both failed.
   - **It happens even when the tray does not scroll.** The browser still claims the pan.
   - **Why tests miss it.** The suite drags only horizontally in landscape (tray.test.tsx:235, :244) and never drags in portrait.
   - **Fix options**, for the builder to choose:
     - (a) Keep the browser's pan only where the tray actually overflows. Use `touch-action: none` on tiles otherwise, and keep `pan-y` on the tray's gaps and headers.
     - (b) Set `touch-action: none` on the tiles and decide in JS after the drag threshold. Movement mostly along the axis that stays inside the tray scrolls it (`scrollTop`/`scrollLeft`). Anything else, or leaving the tray, calls `beginPlacement(part, pointer)`.
     - (c) Start the placement whenever the press leaves the tray's box, whatever the angle. This needs (b)'s `touch-action`, because after `pointercancel` there is no pointer to hand over.
   - **Keep the Back-swipe protection.** Whatever the fix, keep the CI protection (`overscroll-behavior`, no sideways page pan in the library). Add browser tests for a steep diagonal in landscape and for an upward and a shallow diagonal drag in portrait, inside the 1180×820 viewport.

2. **Minor · remove targets have one owner too many**
   - **Where.** packages/app/src/tray/tray.tsx:53–56.
   - **What happens.** `CanvasHandle.setRemoveTargets` replaces the whole list (canvas renderer/surface.ts:390, placement/controller.ts:274, wiring/controller.ts:205). The tray sets `[trayRegion]` on every new canvas. Any second caller will silently overwrite it, or be overwritten, depending on effect order.
   - **The arena strip.** task/4.5 does not call it yet; its README item 8 says the strip is "not yet a remove target" for this reason. app docs/run-loop.md:9 on main already says both the tray and the strip are remove targets.
   - **Recommendation.** One owner: the Shell, which holds the canvas and both `<section data-region>` elements, which are always in the DOM. It should call `canvas.setRemoveTargets([trayRegion, arenaStripRegion])` in one effect keyed on `canvas`. Then remove the call from tray.tsx. Do this in whichever of 4.2 and 4.5 merges second, or as a follow-up micro-task. A context hook such as `useRemoveTarget(ref)` that collects regions is the fallback if a later panel needs to opt in.

3. **Minor · ground rule 8 · iPad VoiceOver may never reach the places list**
   - **Where.** packages/app/src/tray/tray.tsx:121.
   - **What happens.** The keyboard and screen-reader path depends on `click.detail === 0`. If iPadOS VoiceOver's double-tap arrives as a pointer tap, a VoiceOver user gets tap-then-tap: the tile is marked, and the next activation lands somewhere on the canvas. They never get the list of places. The builder flagged this as untested.
   - **Recommendation.** Check it on a device at the next human gate. If it fails, add an affordance that does not depend on how the tile was activated, such as a visually hidden "Places for the chassis" button per tile.

4. **Minor · README and test describe Space, which is Run in the app**
   - **Where.** packages/app/README.md:30 and test/browser/tray.test.tsx:280.
   - **What happens.** Both say Space on a tile opens the places list. On main, task 4.4 makes Space Run and Stop wherever focus is, except in text fields (run-bar/keys.ts, D42), and keeps Space from activating a focused button. In the merged app, Space on a tile toggles Run, and only Enter opens the list. The tray test passes only because it mounts the shell without the Run bar.
   - **Fix.** After merging main, change the README to "Enter or a screen reader's activation". Change the test to Enter, or mount the Run bar and assert that Space runs.

5. **Nit · keyboard test focuses the tile directly**
   - **Where.** test/browser/tray.test.tsx:258.
   - **What happens.** It calls `.focus()` rather than reaching the tile with Tab.
   - **Why it is only a nit.** My probe confirms Tab reaches it.
   - **Optional fix.** A Tab-only step would pin the D84 path to the keyboard alone.

## Questions for Drew

1. **Should the tray stop placement at the kit quantity?** Default: no. The tile shows `× N`, and the child may place more. A cap needs a "none left" state the brief does not describe.
2. **Which kit does the sandbox tray hold?** Default: the kit at the child's level, as built (`kitForLevel`, D68), and the challenge's kit when Home picks a challenge (task 4.5).
3. **What should tapping a library card open?** Default: nothing yet. Once the spec card takes a part type, a tap opens that part's spec card read-only.
4. **Should the library say parts can be pulled into builds from Level 3?** Default: no line, since the brief does not give one.
5. **How should the tray and the arena strip share remove targets?** Default: the Shell owns one `setRemoveTargets([tray, arenaStrip])` call (minor 2).
6. **iPad VoiceOver:** may it wait for a device check at the next gate? Default: yes. The `detail === 0` path stays, and a per-tile "Places" button is added only if the device check fails (minor 3).
7. **Should a tap on the backdrop close the Parts Library?** Default: no. Close, Escape, Run and tucking the tray close it, as built.
8. **For the major finding: which drag behaviour for the tray?** Default: option (b). Tiles take the gesture themselves and scroll the tray only for a drag that stays along it, so any drag towards the canvas places the part.
