## Findings

- **F1 · Medium · done-when (task 6.2), ground rule 14.** `packages/app/test/telemetry/emitters.test.ts:41`, `:100`. The enumeration is a text match on `emitTelemetry(` and on `telemetry.add|put|…(`. It catches the ordinary way to add an emitter. It misses an aliased import, a generic or optional call, a direct `localSink(…).add`, and `db.table('telemetry')`.

  The registry still guards every `emitTelemetry` call at runtime, whatever its spelling, so an aliased call can only emit a listed kind with listed fields. The two sink paths bypass the registry entirely, because `localSink.add` (`packages/app/src/telemetry/emit.ts:22-27`) keeps whatever event it is given.

  Suggested fix:
  - validate in the sink as well, with `eventOf`, or make `localSink` module-private (it is re-exported at `telemetry/index.ts:4`);
  - fail the test on any import of `emitTelemetry` under another name, and on `table('telemetry')`;
  - widen the call regex to allow `<…>` and `?.`.
- **F2 · Medium · D10/D13 local-first.** `packages/app/test/telemetry/emitters.test.ts:111-112`, `packages/app/src/telemetry/emit.ts:43`. The no-network check reads only files under `src/telemetry/`. `withTelemetry` takes any `TelemetrySink`, so a sink that sends, written in `sync/` or `store/` and passed in `open.ts`, would pass every test. Today the only sink is `localSink`, and `open.ts` uses the default. Pin this with a test: `open.ts` calls `withTelemetry` with two arguments only, or the sink parameter is removed until a host and consent exist.
- **F3 · Medium · measure fidelity (brief Section 14, Sandbox return).** `packages/app/src/run-bar/record.ts:106`, `packages/app/src/challenges/home.tsx:153`. A session starts only on the first Run or on a build opened from Home. A challenge is always opened from Home, so challenge sessions are always counted. A sandbox session where the child only builds, without a Run, emits nothing. That biases the 50% sandbox-return rate downward. This is the builder's question 1, and the default suggested below would fix it.

## Verified as asked

- **No identifying data.** Fields are closed sets (`mode`, `step`, `what`, `goalMet`), positive integers (`runNumber`), or challenge ids checked against the content. Beside these, each row keeps only `at` and the local profile UUID. The emitters never pass part ids, build ids or names, or hint triggers. Extra fields, missing fields, free text and unknown challenges are all refused (tested).
- **Not synced.** `SyncCollection` has no telemetry member, nothing writes `changes` for telemetry, and `changes.ts:54` only adds the table to the transaction scope so removal can delete from it. The test checks the outbox holds only profiles.
- **Deleted with the profile.** `profiles.ts:104` deletes in the same transaction as the profile. `localSink.add` checks the profile inside its own transaction, so an emit racing a removal cannot leave an orphan row (tested). The removal warning in the parent view names events.
- **Section 14 coverage.**
  - Unscripted-build pass rate: served by `run` (challenge, runNumber counted per challenge across blueprints, goalMet).
  - Sandbox return: served by `session-start` plus `at`, with F3's bias.
  - Fault fixing: served by `run` `at` on breakdown challenges, timed from the first Run, not from when the breakdown was opened (Q3).
  - Transfer: served by `export`.
  - Parts named: comes from the card game's own records (5.4), with no event needed.
- **One session start per session.** The app makes one `forProfile` scope per opening (`index.ts:78`, again on a profile switch). Home and the Run recorder share it, so the `once` guard holds.
