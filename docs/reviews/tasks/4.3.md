## The four judgements asked for

### 1. Is "without truncation" honest when Level 2 cards scroll? Yes.

I measured this myself with a throwaway Chromium probe, using the real shell, the real content and reduced motion. It lived in the git-ignored `packages/app/node_modules/.review/` and is deleted.

- **Fit.** The panel is 320 × 308 (clientWidth × clientHeight 319 × 307). At Level 1 all 14 cards fit with the macOS system face. At Level 2 only the two wheels fit. The others are over by:

  | Over by | Cards |
  | --- | --- |
  | 16 px | 2-cell battery pack, switch |
  | 18 px | LED |
  | 36 px | buzzer, caster |
  | 38 px | servo motor |
  | 53 px | DC motor |
  | 56 px | 1-cell battery pack, bumper switch |
  | 76 px | gearbox |
  | 125 px | chassis |
  | 278 px | motor driver |

- **Pointer.** One mouse-wheel event over the name scrolled every overflowing card to the bottom.
- **Touch.** A CDP finger drag scrolled every overflowing card. On the motor driver it worked from a text line, from the ports and from a choice button.
- **Keyboard.** The panel itself is not a tab stop, but it does not need to be:
  - with focus on the speak-it button, ArrowDown and PageDown scroll the panel;
  - Tab to a setting scrolls it into view.

  The one case left is a card with no speak-it button (no speechSynthesis) and no setting. Chromium then makes the scroller focusable itself; Safari does not (finding 7).
- **Screen reader.** The last line of every card, the popular-mechanics line or the safety note, is a non-ignored node in Chromium's accessibility tree for the test frame. The panel is `inert` only while hidden.

So nothing is clipped and every line is reachable by all four paths. "Fits without scrolling where possible" is not met at Level 2 (see Q1).

### 2. Does speak-it read exactly the visible words? Almost.

For every Level 1–2 card at Level 2, I compared the words of `spokenLines(card)` with `card.innerText`:
- **Nothing extra** is read.
- **Missing words**: only the labels of choice options that are not selected. The DC motor's "Backward" goes unread, and so do the motor driver's "Stop Backward Stop Backward".

This is deliberate (settings.tsx:30 marks only the checked label `data-speak`; the README's Speak-it section says so). The child then hears "Motor A, Forward", which carries the state. It is still not "the exact on-screen words" (finding 1, Q2).

In Run, readouts (label, then value) and failure lines are read in the order shown (browser test). The rate is 0.9, a second press cancels and starts again, and there is no button without speechSynthesis.

## Joining the runFrames wiring with task 4.4

`git merge-tree --write-tree task/4.4 task/4.3` gives tree ec2c5b2 with one conflict, in packages/app/src/App.tsx at the `slots` line. Each branch rewrites the same `useMemo`. The README auto-merges, and nothing else overlaps.

4.4 does not call `runFrames.push` itself. It hands out its `RunLoop` through `RunBar`'s `onLoop` prop, and `RunLoop.subscribe((state, frame) => …)` gives every frame in tick order, plus a frameless call on each phase change. Stop sets phase `build`; a failed Run sets `failed`.

Whichever branch merges second should resolve the conflict to keep both slots and add a small adapter in App.tsx:

```tsx
const runFrames = useMemo(createRunFrames, []);
const joinRunLoop = useMemo(() => {
  let off: (() => void) | undefined;
  return (loop: RunLoop | null) => {
    off?.();
    runFrames.clear();
    off = loop?.subscribe((state, frame) => {
      if (frame) runFrames.push(frame);
      else if (state.phase !== 'spin-up' && state.phase !== 'running') runFrames.clear();
    });
  };
}, [runFrames]);
const slots = useMemo<ShellSlots>(
  () => ({
    ...PLACEHOLDER_SLOTS,
    specCard: <SpecCard frames={runFrames} />,
    save: <SaveControl saving={saving} />,
    runBar: <RunBar onLoop={joinRunLoop} />,
  }),
  [saving, runFrames, joinRunLoop],
);
```

- Clear on `build`, `failed` and `loading`. Otherwise the last frame of the previous Run would show for a render when Run mode starts again.
- Do not copy RunBar's own slow-motion filter: the card wants every frame.
- RunBar reads `onLoop` through a ref, so a stable callback is enough and the loop is not rebuilt.
- After the join, add one app-level test: Run, check a readout, Stop, check the card shows none.
- 4.4's `RunLoop.input()` already names "the spec card" as a caller. A switch-flip control on the card is unbuilt (finding 5).
