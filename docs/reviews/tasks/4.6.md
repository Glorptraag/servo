## Builder decisions

1. **An offer draws the next drawn rung and pulses the button, and never does do-it: agree.** This is the conservative reading of ground rule 4 and brief Section 5, since only a child's tap changes the build. When only do-it is left, the button pulses and nothing changes (controller.ts:166–171, tested).
2. **Do-it's line shows beside the button: agree.** Brief Section 12 says do-it "says what it did". It is `aria-hidden`, and the same line goes to the status region, so a screen reader does not hear it twice.
3. **Missed Runs are judged from the run loop's frames with GoalWatch: agree.** It is the same judge as `judgeRun` and the goal line. It works with no store, and a Run stopped in spin-up does not count (`stepped`). The order is safe: `halt()` puts the canvas back in Build mode and runs `onEnd` (the recorder) before the loop emits `build`, so the offer's hint use comes after `recorded(count)` takes the Run's own uses.
4. **An ambiguous type target uses the first matching part: acceptable, with a caveat (finding 3).** The ghost wire and do-it can disagree when the build has two parts of the target type.
5. **"Hint", with no reason when it is unavailable: agree.** This follows rule 7. The button stays `aria-disabled`, so keyboard and screen-reader users still reach it, as the Run button does.

## Findings

1. **Medium · correctness / rule 9 (hint shown as behaviour must be true) · packages/app/src/hints/controller.ts:159, :222, :253.** After do-it fixes a breakdown, the fault ladder comes back about a part that is no longer faulty.
   - **Why:** `faults` is only replaced when a Run ends. After do-it on one-motor-backwards, `chooseLadder` still finds the `reversed` fault on motor-right, so the same ladder stays with `doneOn` set.
   - **What the child sees:** any later edit (even moving a part, because `runKeyOf` includes positions) makes `sync` reset `next` to 0. The Hint button becomes available again and draws "This motor turns the other way" on a motor that is now wired correctly. It also logs those uses.
   - **What happens next:** the ladder's do-it then no longer fits (the wires are gone), so the button rests after the drawn rungs.
   - **Possible fixes:** drop the trigger part's fault from `this.faults` once do-it succeeds, or once the build changes in the wires that touch that part.
   - **Missing test:** "do-it on a fault ladder, then edit, then tap" in `test/hints/controller.test.ts`.
2. **Low · rule 9 · controller.ts:253 with meet-the-switch ladder 2 (no trigger).** A ladder with no trigger always applies. After its do-it, any later edit starts it again, and "Side B sends power on to the motor" pulses side B even though it is already wired. This is mostly content: an always-on ladder last in the list. Worth the same fix as finding 1, or a content rule that the last ladder should carry a trigger (question 1).
3. **Low · rule 1/9 consistency · packages/app/src/hints/ladder.ts:142–147 against packages/canvas/src/selection/hints.ts:39–44.** A by-type end that the trigger does not narrow (the switch in drive-and-light) disagrees between the two:
   - The canvas ghost wire draws a line to every matching part.
   - Do-it connects the first part, in id order, that `applyEdit` accepts.
   With two switches, the ghost wire shows two lines and do-it picks one of them. The Level 1–2 examples have one switch, so this is not visible today (decision 4).
4. **Low · test gap · packages/app/test/browser/hints.test.tsx:5.** The header comment says do-it is "one Undo step", but no hint test presses Undo after do-it. The code path is sound: `canvas.apply` with a batch is one `edit` event, which run-bar.tsx:121 turns into one `history.edited`. Still, one Undo after do-it, asserting `start` is back, would pin it.
5. **Low · robustness · packages/app/src/hints/hint-button.tsx:37, :56.** The effect that clears the `HintLog` and rebuilds the controller depends on `loop` and `content`, not only on `challenge`. If the run loop is ever replaced (a new canvas) between a hint and the next Run, the uses waiting to be recorded are dropped and the ladder's place is lost. This does not happen in the app today, because there is one loop per canvas. Narrowing the clear to a change of challenge would be safer.
