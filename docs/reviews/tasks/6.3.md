## Probes

### Workflow security (release.yml)

- **Permissions.** Only `contents: read`. The workflow runs only on a pushed `v*` tag. It has no `pull_request` trigger, so forks never reach the secrets.
- **Pinning.** All four actions are pinned by a 40-hex SHA, each checked against its tag through the GitHub API:
  - checkout v7.0.1, setup-node v7.0.0 and upload-artifact v7.0.1 point at the pinned commits;
  - pnpm/action-setup v6.1.0 is an annotated tag that dereferences to its pinned commit.
- **Secrets.**
  - `SERVO_INVITE_SEED` reaches only the "Build the release" step, and the tool strips it from `pnpm build`'s environment (cli.ts:59-65, tested).
  - `DEPLOY_TOKEN` reaches only the Deploy step. The job-level `HAS_DEPLOY_TOKEN` holds only `true` or `false`.
  - The tag and the invite count reach the script through `env`, never through `${{ }}` inside `run`, so a tag name cannot inject a command.
  - No step echoes a secret.
- **Codes.**
  - The 10 codes appear only in `private/invite-codes.txt`. I searched for all 20 forms (plain and dashed) and the seed in `web/`, `content/`, `release.json`, `GITHUB_OUTPUT`, the summary and the console output, and found none.
  - All 10 hashes are in the web build.
  - `dist/` is gitignored (`git check-ignore`: .gitignore:2).
  - The codes artifact is kept 7 days. `gh` reports the repository as PRIVATE, so only collaborators can download it, which D3 and the README assume.
- **Deploy.** With no token, Deploy and Tester URL are skipped, "Deploy skipped" writes the reason to the summary, and the job stays green. With a token alone, Deploy fails with "no deploy command" after the uploads, as designed and documented.
