## Findings

1. **Major (brief Section 9, focus states: "shows what flows on it").**
   - **Where:** `packages/canvas/src/selection/controller.ts:353-358`, with `layOutCallout` in `src/placement/overlays.ts:93-110`.
   - **What is wrong:** The wire label avoids only sockets and the bin. It is stacked row by row above or below the wire's middle until it fits, with no limit on distance and no check against other lines. In the committed `focus-wire.png`, the label for w8 (the horizontal battery-to-switch line) lands about 140 CSS px below w8, right on top of a different power line, which it hides. In a Level 2 build, "power" would sit just as readily on a yellow signal line. That teaches the wrong thing, and the label is the whole point of this focus state.
   - **Fix:** Keep the label off every other line's 24 px hit corridor, and keep it within a short reach of the selected line. For example, put it on the line itself as a pill, or draw a leader to it. Then add a pixel probe that the label is drawn next to the selected wire (finding 2).
2. **Minor (task done-when, "screenshot tests for each focus state").**
   - **Where:** `test/browser/selection.test.ts:332-360`; the tolerance is set in `packages/canvas/vitest.config.ts:46`.
   - **What is wrong:** The screenshot tolerance is `allowedMismatchedPixelRatio: 0.005`, which is 19,352 pixels at 2360 × 1640. I copied `focus-wire.png` and painted over the label with the same region from `focus-linkage.png`. The label-free copy differs from the reference by only 10,124 pixels, so it would pass.
   - **What else is unguarded:** `probe.wireLabel` reads the callout's `visible` flag, so it catches a hidden label. It does not catch a label drawn in the wrong place, on the wrong layer, or under the build. The selected part's ring is not probed either: `probe.emphasis(...) === 'highlighted'` reads the view's state, and a ring outline is roughly 5,000 to 6,000 pixels, under the tolerance.
   - **Fix:** Add pixel probes for the label (near the wire's middle) and for the ring (on the tile's outline).
3. **Minor (rule 8, the paths give the same result).**
   - **Where:** `wiring/controller.ts:636-642` (`clearSelection` reports `undefined`), `placement/controller.ts:729-732` and `:893`, and `selection/controller.ts:241`.
   - **What is wrong:** In Build mode, a tap that moves the selection from a wire to a part emits an extra `null` before the new selection: `[wire, null, part]`. So does wire to prop, part to prop, and prop to part. The same change by `select`, by the list view, or by a tap in Run mode emits one event. `test/browser/selection.test.ts:123` asserts the extra `null`. The spec card does not misbehave, because the `null` never replaces a part selection except where the card should close anyway. But the stream depends on the path, and task 3.8's parity harness may compare event streams.
   - **Fix:** Have selection swallow a source's `undefined` while the same tap reports a new subject. Alternatively, defer the clear to the end of the tap.
4. **Minor (correctness).**
   - **Where:** `placement/controller.ts:729-732`.
   - **What is wrong:** A tap on one of the child's props runs `tapped(event)` and then always reports `('prop', id)`. When a tray part is waiting for its tap (`incoming`), or a part is being relocated, that tap lands the part and also selects the prop under it.
   - **Fix:** Report the prop only when `tapped` did not land a placement or a relocation.
5. **Minor (interface: `ListView.hint` is "the rung drawn on the canvas now").**
   - **Where:** `selection/controller.ts:130-132`.
   - **What is wrong:** `shownHint` ignores the mode. In Run mode the rung is hidden, but the list view still reads it out, and `test/browser/selection.test.ts:469` asserts this. The app probably clears hints on Run, so the impact is small.
   - **Fix:** Return undefined in Run mode, or document that the text twin persists while the rung is hidden.
6. **Minor (performance, brief Section 13).**
   - **Where:** `selection/controller.ts:385-396`.
   - **What is wrong:** While a rung pulses, `stepPulse` calls `surface.requestFrame()` on every animation frame. That redraws the whole canvas at the display rate for as long as a hint is waiting, which can be minutes on a tablet. `frame-time.test.ts` does not cover a pulsing hint.
   - **Fix:** Consider a lower pulse frame rate. Alternatively, leave it, but add a pulsing hint to the frame-time test.
7. **Minor (test coverage, ground rule 6).**
   - **Where:** `packages/tools/test/lint-rules.test.ts:71`.
   - **What is missing:** The committed cases cover only `export *` from app. They do not cover:
     - parent;
     - the `import type`, `import()` type and dynamic `import()` forms that the behaviour entry has cases for;
     - a message test for the new "The app reaches the canvas through @servo/canvas." line.

     All of these work today (see the probe above). A relative `./testing.ts` import from canvas's own `src/` is not blocked either, so `index.ts` could re-export the entry. Review would catch that, but a lint case would be cheaper.
